## 1. 项目总体概述

**一句话定位**：一个用「大模型 + 多智能体」做**能源分析与优化**的演示级系统——用户用自然语言提问，
系统自动理解意图、调度 6 个专职子智能体调用领域工具取数计算，最终给出可执行、可量化的结论。

**形态**：

- 后端：Python + FastAPI，提供静态页面与 SSE 流式问答接口；
- 智能体：约 200 行自研的「Supervisor + 子智能体」轻量多智能体框架；
- 前端：无构建步骤的原生 HTML/CSS/JS + ECharts，ChatGPT / Claude Code 风格界面；
- 数据：贴近我国电力现状的模拟数据 + 8 个领域工具（纯函数，可替换真实接口）；
- 模型：OpenAI 兼容协议，默认 DeepSeek，换 `base_url`/`model` 即可切换任意兼容模型。

**核心价值**：把「能源优化」这一复杂、专业、需跨领域协同的任务，拆解为可协作、可观测、
可扩展的智能体工作流；同时作为一份**最小可运行的多智能体框架教学样本**，把 subAgent、
ReAct 循环、结构化决策、两阶段流式等现代 Agent 技术讲清楚。

## 2. 项目背景

### 2.1 解决什么问题（行业背景）

当前我国电力系统正经历深刻变化，产生一系列真实而紧迫的工程问题：

| 背景事实 | 带来的具体问题 |
|---------|--------------|
| 光伏、风电装机占比快速提升 | 出力随机波动，弃风弃光与消纳压力增大 |
| 空调、电动汽车等负荷增长 | 峰谷差率逐年扩大，电网调峰与设备利用率承压 |
| 分时电价、电力市场化推进 | 峰谷价差扩大，储能 / 需求响应出现经济空间，但缺乏落地方案 |
| 「双碳」目标 | 企业面临碳排放核算、绿电匹配、减排路径规划等新诉求 |
| 能源互联网 / 虚拟电厂建设 | 需要「源、网、荷、储」协同调度，而非各环节孤立优化 |

这些问题的共同特点是：**数据分散、专业性强、需要跨领域协同决策**。传统做法依赖人工经验与
割裂的工具；而大模型 + 多智能体恰好匹配「理解意图 → 调用专业工具 → 协同分析 → 给出结论」
这条链路。

### 2.2 目标用户与适用场景

**目标用户**：

- 园区 / 工厂 / 商业综合体的能源管理人员：做负荷预测、储能套利、节能改造、碳核算；
- 售电公司、虚拟电厂运营商：做源网荷储协同调度与需求响应分析；
- 电力 / 新能源方向的开发者、学生、研究者：学习「大模型 + 多智能体」在能源领域的落地范式。

**适用场景**：

- 负荷预测与削峰填谷；
- 光伏 / 风电出力与消纳分析；
- 储能充放电策略与峰谷套利；
- 源网荷储协同调度（虚拟电厂 / 微电网）；
- 能耗诊断与节能改造；
- 碳排放核算与降碳路径。

### 2.3 满足什么需求

1. **降低专业门槛**：用自然语言替代专业工具操作，把领域知识沉淀到智能体提示词与工具里；
2. **跨领域协同**：主控智能体自动把任务路由给合适的子智能体并汇总，替代人工串流程；
3. **可量化可执行**：输出带数字的结论（收益、削峰率、减排量）而非空泛建议；
4. **过程可观测**：前端实时展示「哪个智能体、调了什么工具、返回了什么」，增强可信度；
5. **低成本快速验证**：无需真实数据接入，用模拟数据即可跑通全链路，验证思路后再替换数据源。

### 3.3 关键设计理念

1. **小而精**：核心框架约 200 行，无 LangChain/LangGraph 等重依赖，逻辑透明；
2. **子智能体即工具**：主控把每个子智能体封装成可调用的工具，实现层级委派（现代 subAgent 模式）；
3. **结构化 JSON 决策**：不依赖模型原生 function-calling，对所有 OpenAI 兼容模型一视同仁；
4. **两阶段输出**：工具循环阶段非流式（稳定），最终回答阶段真流式（体验好）；
5. **纯函数工具**：数据与计算与框架解耦，替换数据源无需改动 Agent 框架与前端。

## 6. 用了什么技术、为什么用它、解决了什么问题

### 6.1 大模型接入层：OpenAI 兼容协议 + `openai` SDK

- **用了什么**：`openai` 的 `AsyncOpenAI` 客户端，通过 `base_url` + `model` + `api_key` 接入；
- **为什么**：DeepSeek、通义千问、智谱 GLM、OpenAI 等国内外主流模型都提供 OpenAI 兼容接口，
  一套代码即可全部覆盖；
- **解决了什么**：模型厂商锁定问题——换模型只需改 `.env`，无需改任何代码。

### 6.2 智能体框架：自研 Supervisor + 子智能体

- **用了什么**：约 200 行自研框架（`Tool` / `Agent` / `Supervisor`），而非 LangGraph；
- **为什么**：LangGraph 是业界标准，但依赖较重、版本升级常带来兼容问题（参考项目里就出现了
  `ChatTongyi.model_rebuild()` 这类补丁）；本项目定位「小而精、能跑起来」，自研能把多智能体
  协作机制讲透，又避免重依赖；
- **解决了什么**：复杂能源任务的拆解与协同——把「储能优化」「碳核算」等专业任务交给专职智能体，
  由主控统一调度汇总，避免单个大模型「什么都知道但什么都算不准」。

### 6.3 决策协议：结构化 JSON 而非原生 function-calling

- **用了什么**：让 LLM 输出 `{"action":"tool","tool":...,"args":{...}}` 或 `{"action":"finish",...}`；
- **为什么**：原生 function-calling 在不同厂商间格式略有差异、流式解析易出错；
- **解决了什么**：对任意 OpenAI 兼容模型一视同仁，且工具调用过程完全透明、可观测。

### 6.4 后端：FastAPI + SSE

- **用了什么**：FastAPI + `StreamingResponse`（`text/event-stream`）；
- **为什么**：异步、轻量、原生支持流式；
- **解决了什么**：用极少代码承载「流式问答接口 + 静态前端托管」。

### 6.5 前端：原生 HTML/CSS/JS + ECharts

- **用了什么**：手写 Markdown 渲染器 + SSE 解析 + ECharts；
- **为什么**：无构建步骤、可控性强、零依赖；
- **解决了什么**：做出 ChatGPT 级界面 + 源网荷储可视化，且易部署（一个 `python app.py` 就起）。

### 6.6 数据层：纯函数模拟数据

- **用了什么**：`mock_data.py` 中的常量 + 纯函数工具；
- **为什么**：演示需要可运行、数据可控；
- **解决了什么**：无需真实数据接入即可端到端跑通，且后续替换数据源不改框架。

## 7. 核心技术实现详解

> 本节是本文档的重点：Agent 智能体框架与 MCP 专题做了详尽展开，其余部分给出实现要点。

### 7.1 Agent 智能体框架（重点）

代码位于 `agent/core.py`（约 200 行），由三个核心概念构成。

#### 7.1.1 核心抽象：`Tool` / `Agent` / `Supervisor`

**`Tool`（工具）** —— 一个数据类，描述一个可被智能体调用的能力：

```python
@dataclass
class Tool:
    name: str            # 工具名（LLM 用它来点名调用）
    description: str     # 一句话说明（注入提示词，供 LLM 判断何时调用）
    func: Callable       # 实际执行函数 async func(**kwargs) -> str
    needs_emit: bool     # 是否需要把 emit 回调注入（委派工具需要）
```

**`Agent`（智能体）** —— 一个「系统提示词 + 工具集」的执行单元，能独立完成一类专业任务。
关键属性：`name`（标识）、`role`（职责描述）、`system_prompt`（专业提示词）、`tools`（可用工具列表）。

**`Supervisor`（主控智能体）** —— 继承 `Agent`，额外持有 `subagents` 列表，并把每个子智能体
包装成工具，从而实现「层级委派」（见 7.1.4）。

#### 7.1.2 ReAct 决策循环（`Agent.run`）

每个智能体的执行是一个标准的 ReAct（Reasoning + Acting）循环，最多 `max_tool_rounds`（默认 6）轮：

```
┌─────────────────────────────────────────────────────────┐
│ 1. 构造 messages：系统提示词(含工具清单+决策协议) + 用户任务   │
│ 2. 循环（最多 N 轮）：                                     │
│      llm.complete(messages)  → 得到一段文本                │
│      parse_json(text)        → 解析决策 JSON               │
│      若 action != "tool"     → 跳出循环（进入合成阶段）      │
│      否则：查工具 → 不存在则提示重选；存在则：                │
│           emit(tool) 事件                                  │
│           _invoke(tool, args)  → 得到结果文本               │
│           emit(tool_result) 事件                           │
│           把「assistant 决策 + 工具返回」追加回 messages      │
│ 3. 合成阶段：基于 observations 生成最终结论                   │
└─────────────────────────────────────────────────────────┘
```

关键点：**每一轮都把「上一次决策」和「工具返回结果」追加进对话历史**，让模型在「观察」的基础上
继续「思考」，这正是 ReAct 的精髓——模型不是一次规划到底，而是边看数据边决策。

#### 7.1.3 两阶段输出

- **工具循环阶段（非流式）**：用 `llm.complete()` 拿完整决策。因为决策是结构化的 JSON，逐字
  流式解析反而容易出错，整段拿回更稳定；
- **最终合成阶段（流式）**：用 `llm.stream()` 逐块产出最终回答，前端逐字渲染，体验好。

子智能体被主控委派时以 `stream_text=False` 运行：**不流式**、返回**精炼的调研结论**
（`findings=True` 走「调研结论」提示词），供主控汇总；只有主控的最终回答才真流式。这样既保证
了层级委派下数据的稳定传递，又保证了最终用户体验。

#### 7.1.4 子智能体即工具（subAgent 层级委派）

这是本项目体现「现代 subAgent 技术」的核心设计。`Supervisor._delegate_tool` 把每个子智能体
封装成一个工具：

```python
def _delegate_tool(self, agent: Agent) -> Tool:
    async def delegate(emit, task: str = "") -> str:
        return await agent.run(task, emit, stream_text=False)

    return Tool(
        name=f"ask_{agent.name}",
        description=f"委派给「{agent.name}」子智能体处理：{agent.role}。参数 task 为具体指令。",
        func=delegate,
        needs_emit=True,
    )
```

于是主控的工具清单里出现了 `ask_load_forecaster`、`ask_storage_agent` 等 6 个委派工具。
主控在 ReAct 循环中像调用普通工具一样「调用」子智能体，而子智能体内部又跑自己的 ReAct 循环、
调用自己的领域工具——形成**两层嵌套的 ReAct**。这与 Claude Code 等主流平台「把子代理作为工具
调用」的模式一致。

`needs_emit=True` 的作用：委派工具的 `delegate` 需要把 `emit` 回调透传给子智能体，让子智能体
的工具调用轨迹也能一路冒泡到前端。`_invoke` 中通过 `inspect.signature` 判断函数签名，自动注入
`emit` 参数。

#### 7.1.5 工具调用的健壮性设计

- **稳健 JSON 解析（`parse_json`）**：LLM 输出常带 ` ```json ``` ` 代码块或前后杂文，函数先剥
  代码块，再截取第一个 `{` 到最后一个 `}`，最后 `json.loads`；失败返回 `{}`，不会让流程崩溃；
- **参数过滤（`_invoke`）**：用 `inspect.signature` 提取函数实际接受的参数，只传入匹配项，
  避免 LLM 多余参数导致 `TypeError`；
- **异常隔离**：单个工具调用异常被捕获，转为「工具调用出错：...」文本继续流程，不中断整体；
- **工具不存在兜底**：LLM 点到不存在的工具时，追加提示「工具 X 不存在，请重新选择」，继续循环。

#### 7.1.6 事件系统（`emit` 回调）

`Agent.run` 通过异步回调 `emit(dict)` 向外发布事件，前端据此渲染思考轨迹。事件类型：

| 事件 | 字段 | 含义 |
|------|------|------|
| `agent` | `agent`, `content` | 某智能体启动，`content` 为其职责 |
| `tool` | `agent`, `tool`, `args` | 智能体调用某工具及参数 |
| `tool_result` | `agent`, `tool`, `preview` | 工具返回结果（截断预览） |
| `text` | `content` | 最终回答的流式文本块 |
| `error` | `content` | 错误信息 |
| `done` | — | 结束标记 |

事件在 `Agent`/`Supervisor` 内部产生，最终由 `app.py` 的 `emit` 实现送入 `asyncio.Queue`
转为 SSE 帧（见 7.3）。

### 7.2 MCP（Model Context Protocol）专题（重点）

> 用户特别要求：牵涉 MCP 的地方要介绍得更详细一些。本节先说明 MCP 是什么，再讲本项目与 MCP
> 的关系、为何未采用、以及如何演进到 MCP。

#### 7.2.1 什么是 MCP

**MCP（Model Context Protocol，模型上下文协议）** 是一个**开放协议**，用于标准化「AI 应用 /
智能体」与「外部工具和数据源」之间的连接方式，解决的是「模型如何安全、统一地调用外部能力」
这一通用问题。

核心架构是 **Client-Server（客户端-服务器）**：

```
┌──────────────┐      JSON-RPC 2.0        ┌──────────────┐
│  MCP Client  │ ◄──────────────────────► │  MCP Server  │
│  （宿主，如   │   tools / resources /    │ （提供工具/数据│
│   Claude 等） │   prompts 的发现与调用     │   的实现方）  │
└──────────────┘                          └──────────────┘
       传输方式：stdio（本地子进程）或 Streamable HTTP（网络）
```

MCP 定义了三个核心原语：

- **Tools（工具）**：可被模型调用的函数，带名称、描述、JSON Schema 参数；
- **Resources（资源）**：可被读取的数据（文件、数据库记录等）；
- **Prompts（提示词）**：可复用的提示词模板。

**价值**：工具与「模型 / 宿主应用」解耦。一个 MCP Server 写好后，可以被 Claude Desktop、各类
IDE、多个 Agent 框架复用——就像 USB 接口之于外设。MCP 由 Anthropic 于 2024 年底提出后，
已成为连接模型与工具的事实标准，被广泛采用。

#### 7.2.2 本项目与 MCP 的关系：为什么没有直接用 MCP

**本项目没有使用 MCP SDK，而是自己定义了一套 `Tool` 抽象。** 原因有三：

1. **规模不匹配（小而精优先）**：本项目的工具是**同进程内的 Python 纯函数**（`mock_data.py`）。
   MCP 会引入「独立 Server 进程 + JSON-RPC 编解码 + 传输层」的额外复杂度，对当前规模没有
   功能收益，反而违背「代码凝练、可读性强」的目标；
2. **概念等价，只是未标准化**：本项目的 `Tool(name, description, func)` 与 MCP 的 Tool
   （名称 + 描述 + 参数 Schema）是**同一份契约**——都是「给模型一个名字和说明，让模型点名调用」。
   区别仅在于：本项目直接调 Python 函数，MCP 通过协议远程调 Server；
3. **零依赖、易运行**：不引入 MCP SDK，`requirements.txt` 只需 4 个依赖，任意环境 `pip install`
   即可跑。

一句话总结：**本项目用的是「MCP 想标准化的事」的最小本地实现**，把协议的复杂度留在了协议层，
专注于把「工具如何被智能体调用」这件事讲清楚。

#### 7.2.3 本项目的「工具」与 MCP 工具的对照

| 维度 | 本项目 `Tool` | MCP Tool |
|------|--------------|----------|
| 名称 | `name: str` | `name` |
| 说明 | `description: str`（注入提示词） | `description` |
| 参数约定 | `args` 自由字典，运行时用 `inspect.signature` 过滤 | JSON Schema（调用前即校验） |
| 调用方式 | 进程内直接 `await func(**kwargs)` | JSON-RPC `tools/call` 跨进程 |
| 可观测性 | `emit` 事件冒泡到前端 | 协议层可记录 |
| 复用性 | 仅本项目内 | 跨宿主 / 跨应用复用 |

可见本项目在「名称 + 描述 + 调用」上与 MCP 高度一致，弱化的是**参数 Schema 的强约束**和
**跨进程复用**——这两点在单进程演示里并非刚需，反而 MCP 的 JSON Schema 是更严谨的演进方向。

#### 7.2.4 如何演进到 MCP

如果后续要把本项目的能源工具推广给更多 Agent 宿主复用，可以这样接入，**无需改动 Agent 框架**：

1. **把工具发布为 MCP Server**：用官方 Python SDK 把 `mock_data.py` 里的 8 个函数包装成
   一个 MCP Server（每个函数一个 Tool，参数加 JSON Schema）；
2. **`Tool.func` 换成 MCP 客户端调用**：让 `Agent` 的 `Tool.func` 内部改为调用 MCP 客户端的
   `tools/call`，其余 ReAct 循环、两阶段流式、事件系统全部不变；
3. **收益**：同一套能源工具可被 Claude Desktop、其他 Agent 框架复用；同时本项目也能反过来
   作为 MCP Client，拉入第三方 MCP Server（如天气、数据库查询）扩展能力。

**结论**：MCP 与本项目不是替代关系，而是**「标准化协议」与「轻量教学实现」的互补关系**。
理解本项目的 `Tool` 抽象，就理解了 MCP 工具的本质；把 `Tool.func` 换成 MCP 调用，就完成了
从「本地工具」到「标准工具」的升级。

### 7.3 SSE 流式后端（`app.py`）

`/api/chat` 用 `StreamingResponse` 实现 Server-Sent Events：

```python
async def event_stream():
    queue = asyncio.Queue()

    async def emit(event: dict):       # 把 Agent 事件塞进队列
        await queue.put(event)

    async def run():
        try:
            await supervisor.run(question, emit, stream_text=True)
        except Exception as exc:        # 捕获 LLM/工具异常，友好反馈
            await emit({"type": "error", "content": ...})
        finally:
            await emit({"type": "done"})

    task = asyncio.create_task(run())   # 智能体在后台任务中运行
    while True:
        event = await asyncio.wait_for(queue.get(), timeout=300)
        yield f"data: {json.dumps(event, ensure_ascii=False)}\n\n"
        if event["type"] == "done":
            break
```

**设计要点**：

- **`asyncio.Queue` 解耦**：智能体在独立 `asyncio.create_task` 中运行，`emit` 只负责 `put`，
  生成器只负责 `get` 并 `yield`——两者通过队列解耦，天然支持「生产者快、消费者慢」的背压；
- **SSE 帧格式**：每个事件一行 `data: <json>\n\n`，前端按 `\n\n` 切帧解析；
- **关键响应头**：`Cache-Control: no-cache`（禁止缓冲）、`X-Accel-Buffering: no`（禁用 Nginx
  代理缓冲，保证实时性）；
- **超时兜底**：`wait_for(queue.get(), timeout=300)` 防止智能体卡死导致连接永久挂起；
- **错误分级**：空消息 `400`、未配 Key `503`（提示复制 `.env.example`）、运行期异常转 `error`
  事件（401/Key 相关时附排查提示）。

### 7.4 前端流式渲染（`static/app.js`）

- **SSE 消费**：用 `fetch` + `res.body.getReader()` 读流，`TextDecoder` 解码，按 `\n\n` 切帧、
  再按 `data: ` 前缀解析出 JSON 事件（不依赖原生 `EventSource`，因为需要 POST + JSON body）；
- **事件分发**：`agent`/`tool` → `addTrace` 追加轨迹；`tool_result` → `markToolDone` 给对应
  工具打勾并回填结果预览；`text` → 累加 `acc` 并 `setText` 重渲染；`error` → 显示错误；
- **思考过程轨迹**：默认折叠，点击展开；每步展示「🤖 智能体 / 🔧 工具」图标、智能体名、工具名、
  参数 JSON 与返回预览；
- **Markdown 渲染**：手写一个约 50 行的渲染器，支持代码块、标题、列表、表格、加粗、行内代码、
  链接、分隔线（先用占位符保护代码块，最后回填，避免代码内容被误转义）；
- **流式光标**：内容末尾追加 `.cursor`，CSS `@keyframes blink` 实现闪烁；
- **会话持久化**：`localStorage` 存 `{currentId, order, conversations}`，新建/切换/刷新不丢。

### 7.5 领域数据与调度算法（`data/mock_data.py`）

- **数据**：三个区域（园区 A/B、工厂 C）的负荷峰值、光伏/风电装机；24h 负荷双峰形状、光伏钟形、
  风电波动形状；四段式分时电价（谷 0.32 / 平 0.68 / 峰 1.05 / 尖峰 1.30 元/kWh）；储能参数
  （20MWh/5MW/SOC 0.4/效率 0.92/最低 SOC 0.1）；分项能耗；碳排放因子（电网平均 0.5703 kgCO2/kWh 等）。
- **调度算法 `optimize_dispatch`**：规则贪心——先算净负荷 `负荷 - 光伏 - 风电`，再**按电价从低到高
  排序充电、从高到低排序放电**，在功率与 SOC 约束下给出充放电计划，最后对比优化前后购电成本与
  削峰率。这是「储能峰谷套利」的经典简化实现，数值合理、可被 LLM 解读；
- **纯函数约束**：所有工具函数同步、无副作用、返回可读文本——既便于测试，也便于替换真实数据源。

## 8. 一次完整请求的生命周期

以「优化园区 A 的储能充放电策略」为例，端到端时序：

```
浏览器                     app.py                      Supervisor                 storage_agent
  │ POST /api/chat          │                              │                            │
  │────────────────────────►│                              │                            │
  │                         │── supervisor.run(emit) ─────►│                            │
  │                         │                              │ emit agent(supervisor)    │
  │                         │◄── SSE: agent ───────────────│                            │
  │                         │                              │ 决策 ask_storage_agent    │
  │                         │                              │ emit tool                 │
  │                         │◄── SSE: tool ────────────────│                            │
  │                         │                              │── delegate(task) ─────────►│
  │                         │                              │                            │ emit agent(storage)
  │                         │                              │◄── (轨迹冒泡) ─────────────│
  │                         │◄── SSE: agent ───────────────│                            │
  │                         │                              │                            │ 决策 get_price_curve
  │                         │◄── SSE: tool ────────────────│                            │
  │                         │◄── SSE: tool_result ─────────│                            │
  │                         │                              │     …再调 get_storage_status、
  │                         │                              │      get_load_curve（同轨迹）…
  │                         │                              │◄── 返回精炼调研结论 ─────────│
  │                         │                              │ 汇总 → llm.stream()         │
  │                         │◄── SSE: text（逐字）───────────│                            │
  │                         │◄── SSE: done ─────────────────│                            │
  │ 前端逐字渲染 + 轨迹 ✓     │                              │                            │
```

全程 3 次 LLM 调用（主控决策、储能智能体决策、主控流式合成）+ 3 次工具调用，形成两层嵌套 ReAct。

## 11. 局限与展望

**当前局限**：

- 数据为模拟数据，未接入真实 SCADA / 交易中心 / 用能平台；
- 调度算法为规则贪心，未做数学优化（可换 MILP / 强化学习）；
- 会话无服务端上下文记忆（仅前端 `localStorage`），多轮追问能力弱；
- 主控为串行委派，未做多子智能体并行下发再汇总。

**展望**：

- 接入真实数据源，工具函数替换为真实接口（框架零改动）；
- 增加**并行委派**：主控同时对多个子智能体下发任务再汇总；
- 引入**规划-执行-反思**更完整的 ReAct 变体，提升复杂任务稳定性；
- 增加会话级记忆与多轮追问；
- 按 7.2.4 将工具演进为 **MCP Server**，实现跨宿主复用；
- 用本地小模型做低延迟路由、大模型做深度分析的分层策略。
