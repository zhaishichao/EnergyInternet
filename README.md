# ⚡ 能源互联网智能体 · EnergyInternet Agent

一个面向「源网荷储」协同与能源节约的**多智能体问答/分析系统**。基于轻量自研的
**Supervisor + 子智能体（subAgent）** 架构，围绕我国电力与新能源发展现状，帮助用户
完成负荷预测、新能源消纳、储能套利、调度优化、能耗诊断与碳核算等任务。

前端为 ChatGPT / Claude Code 风格的网页界面，支持真流式输出与「思考过程」工具轨迹展示。

---

## 1. 项目背景：为什么要做这件事

当前我国电力系统正经历深刻变化，带来一系列真实而紧迫的工程问题：

- **新能源占比快速提升**：光伏、风电装机持续增长，但出力随机波动，带来弃风弃光与消纳压力；
- **负荷峰谷差加大**：空调、电动汽车等负荷增长，峰谷差率逐年扩大，电网调峰与设备利用率承压；
- **分时电价与电力市场化**：峰谷价差扩大，为储能、需求响应创造了经济空间；
- **双碳目标**：企业面临碳排放核算、绿电匹配、减排路径规划等新诉求；
- **能源互联网 / 虚拟电厂建设**：需要「源、网、荷、储」协同调度，而非各环节孤立优化。

这些问题的共同特点是：**数据分散、专业性强、需要跨领域协同决策**。传统做法依赖人工经验与
割裂的工具，而大模型 + 多智能体恰好适合这种「理解意图 → 调用专业工具 → 协同分析 → 给出
可执行结论」的场景。

本项目正是为此构建的一个可运行、可扩展的演示级框架：用多个**专职子智能体**各司其职，
由**主控智能体**统一调度与汇总，把「能源优化」这一复杂任务拆解为可协作的智能体工作流。

## 3. 系统架构

```
用户提问
   │
   ▼
┌─────────────────────────────────────────────────────────┐
│  主控智能体 Supervisor（supervisor）                      │
│  理解意图 → 路由/委派 → 汇总多智能体结论 → 流式输出       │
└───────────────┬─────────────────────────────────────────┘
                │  子智能体即工具（层级委派，subAgent 模式）
   ┌────────────┼────────────┬────────────┬────────────────┐
   ▼            ▼            ▼            ▼                ▼
负荷预测    新能源       储能       调度优化     能耗分析    碳核算
智能体      智能体       智能体      智能体       智能体      智能体
   │            │            │            │            │            │
   └────────────┴────────────┴───── ReAct 工具循环 ───────┴────────────┘
                                        │
                             领域工具（mock 数据，可替换真实接口）
                   负荷曲线 / 风光出力 / 储能状态 / 电价 / 能耗 / 碳因子 / 调度计算
```

**关键设计（体现现代 subAgent 技术）：**

1. **子智能体即工具**：每个子智能体被封装成主控可调用的「工具」（`ask_xxx`），实现层级委派，
   与 Claude Code 等主流平台把子代理作为工具调用的模式一致；
2. **统一 ReAct 循环**：每个智能体在「系统提示词 + 专属工具集」下循环执行
   `思考 → 调工具 → 观察 → 再思考`，最多 N 轮；
3. **两阶段输出**：工具循环阶段非流式（稳定），最终回答阶段真流式（体验好）；
4. **结构化 JSON 决策**：LLM 通过 `{"action":"tool",...}` / `{"action":"finish",...}` 决策，
   不依赖模型原生 function-calling，兼容任意 OpenAI 兼容模型。

## 4. 技术栈：用了什么、为什么用、解决了什么问题

| 技术 | 为什么用 | 解决了什么问题 |
|------|---------|---------------|
| **Python + FastAPI** | 轻量、异步、原生支持 SSE 流式 | 用极少代码承载流式问答接口与静态前端 |
| **`openai` SDK（OpenAI 兼容协议）** | 一套代码对接 DeepSeek / 通义 / GLM / OpenAI | 模型可插拔、不锁定厂商，换 Key 即可切换 |
| **自研轻量多智能体框架**（约 200 行） | 无重依赖、逻辑透明、可离线用 stub 调试 | 避免 LangChain/LangGraph 的版本兼容坑，清晰呈现子智能体架构 |
| **原生 HTML/CSS/JS + ECharts** | 无构建步骤、可控性强 | 做出 ChatGPT 级界面 + 源网荷储可视化面板 |
| **`python-dotenv`** | 极轻量 | 便捷管理 API Key，避免硬编码 |

**为什么不用 LangGraph 而是自研？** LangGraph 是业界标准，但依赖较重、版本升级常带来
兼容问题（参考项目里就出现了 `ChatTongyi.model_rebuild()` 这类补丁）。本项目要「小而精、
能跑起来」，自研一套 ~200 行的核心框架，既把多智能体协作的机制讲清楚，又避免了重依赖。

**为什么用结构化 JSON 而非原生 function-calling？** 原生 function-calling 在不同厂商间
格式略有差异、流式解析易出错；结构化 JSON 决策对所有 OpenAI 兼容模型一视同仁，且工具调用
过程完全透明、可观测。

## 7. 快速开始

### 7.1 环境要求

- Python 3.8+（开发环境为 3.9）
- 一个 OpenAI 兼容大模型的 API Key（DeepSeek / 通义千问 / GLM / OpenAI 均可）

### 7.2 安装依赖

```bash
cd EnergyElectricity
pip install -r requirements.txt
```

### 7.3 配置 API Key

```bash
cp .env.example .env   # Windows: copy .env.example .env
```

编辑 `.env`，填入你的 Key。默认使用 DeepSeek：

```ini
LLM_API_KEY=sk-你的Key
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-chat
```

若使用其它模型，参考 `.env.example` 中的注释切换 `LLM_BASE_URL` / `LLM_MODEL`。

### 7.4 启动

```bash
python app.py
```

浏览器打开 **http://localhost:8000**。

### 7.5 运行测试（无需 Key）

```bash
python tests/test_agent.py
```

### 7.6 示例问题

```text
帮我优化园区A的储能充放电策略，最大化峰谷套利收益
分析园区B的能耗结构，并给出节能改造建议
预测工厂C明日负荷曲线，并给出削峰填谷建议

对园区A做一次源网荷储协同调度优化
什么是虚拟电厂？
```

## 8. 多智能体工作流示例

以「优化园区 A 的储能充放电策略」为例，完整链路：

1. **主控 Supervisor** 理解意图，判定属于储能场景，委派给 `storage_agent`；
2. **储能智能体** 调用 `get_price_curve`（峰谷电价）→ `get_storage_status`（当前 SOC）→
   `get_load_curve`（负荷），必要时再调 `get_renewable_output`；
3. 数据齐备后，储能智能体**流式生成**充放电策略（谷段充电、尖峰放电，量化套利收益）；
4. 主控智能体**汇总并流式输出**最终答案，前端同步展示「思考过程」轨迹与逐字回答。

前端「思考过程」面板会实时显示每一步：`🤖 储能智能体` → `🔧 调用工具 get_price_curve(region=园区A) ✓` 等。

## 9. 数据说明

`data/mock_data.py` 中的负荷曲线、风光出力、峰谷电价、储能参数、能耗分项、碳因子均为
贴近我国电力系统现状的模拟数据（如全国电网平均排放因子 0.5703 kgCO2/kWh、尖峰/峰/平/谷
分时电价等）。所有领域工具均为**纯函数**，后续只需替换函数内部实现为真实数据源
（SCADA / 电力交易中心 / 用能监测平台），**无需改动 Agent 框架与前端**。

## 11. 常见问题（FAQ）

**Q1：没有 API Key 能跑吗？** 框架与前端、测试都能跑（`python tests/test_agent.py`），但
问答需要真实大模型，须在 `.env` 配置 Key。

**Q2：为什么换模型只需改配置？** 因为全部通过 OpenAI 兼容协议调用，`LLM_BASE_URL` /
`LLM_MODEL` 决定用哪家模型。

**Q3：流式为什么用两阶段？** 带工具调用的复杂链路下，先非流式收集数据更稳定，最后一段
纯文本再真流式，兼顾可靠性与体验。
